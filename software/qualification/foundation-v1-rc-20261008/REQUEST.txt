## 3. Create a three-tier testing model

### Tier 1 — focused development tests

Run constantly during implementation.

Target:
- rule-specific acceptance tests
- boundary tests
- UNKNOWN/UNSUPPORTED/negative cases
- local provenance/tamper tests

Goal: seconds to low minutes.

### Tier 2 — affected-family regression

Run after a coherent rule/family change.

Only execute consumers/dependencies actually affected by the changed source or shared infrastructure.

Examples:
- halogen family
- metal family
- source-state/representation family
- SAM/sulfur family
- event/coverage family

Goal: a few minutes.

### Tier 3 — full release qualification

Run only when sealing a batch or Foundation release candidate.

Includes:
- complete regression suite
- isolation suite
- all independent JVM replay
- 65 historical comparisons
- 25 preservation pins
- fresh committed-source clean export
- full ledger/checkpoint generation

Do not run Tier 3 after every leaf predicate.

## 4. Add test dependency metadata

Determine which tests actually depend on which qualified rules/modules.

A change to an I11 leaf should not automatically rerun unrelated Zn, water, SAM and external-data tests unless shared infrastructure changed.

Create a deterministic affected-test selection mechanism.

When shared infrastructure changes—matcher, source graph, evidence serialization, Research Gate, correspondence, geometry engine, etc.—escalate automatically to the broader required tier.

The selection mechanism must fail safe: uncertainty about dependency means include the test.

## 5. Cache only immutable qualified setup

Investigate safe caching of expensive immutable artifacts such as:

- pinned reference source parsing
- immutable catalog parsing
- source digests
- static rule manifests
- immutable graph fixtures
- qualification/reference metadata

Do not cache mutable scientific state or anything whose reuse could hide provenance mismatches.

Every cached artifact must remain keyed by exact source/configuration digest so changed bytes invalidate the cache automatically.

## 6. Parallelize where independence is proven

Identify tests and replay jobs that can execute independently.

Potential candidates:
- unrelated focused rule families
- independent JVM replay pairs
- historical comparison groups
- preservation-pin checks

Do not parallelize tests sharing mutable state, ports, databases, output locations or evidence stores unless isolation is explicit.

Determinism must remain mandatory.

## 7. Eliminate redundant repeated setup

Look specifically for cases where hundreds/thousands of tests repeatedly:

- parse the same immutable source
- hash the same artifact
- recreate the same Research Gate records
- rebuild identical molecular graphs
- reload identical OCL/RDKit/reference material
- reconstruct identical qualification fixtures

Move safe immutable setup to qualified shared fixtures where this does not change scientific semantics.

Do not optimize by weakening source/provenance verification.

## 8. Separate replay modes

During development:

- run replay only for newly affected identities plus required dependency hashes

At release:

- run all historical/replay/preservation checks

Existing historical byte identity remains mandatory for release qualification.
