This endpoint has stable compound identities, explicit computation attribution, source release,

The selected properties are PubChem's own computations, not third-party annotations. Source-use

third-party content in PubChem. Importer attribution checks exclude such third-party values.

ARCHITECTURAL BOUNDARY

Hermes parses external records and emits versioned JSON receipts. Athena consumes that local
receipt contract for scientific review; it does not fetch or parse the PubChem raw response schema.
Hermes never imports Athena, and Athena never imports Hermes in production. The host first calls
Hermes readVerified to reparse/check the projection, then Athena readSourceReceipt/review operations.
This schema boundary avoids moving external-data mechanics into Athena or adding evidence to Gaia.
The OCL module has a new TEST-SCOPED Hermes dependency for the integration fixture only. No new
production dependency, module, backend rename or graph/identity implementation is introduced.

RAW RECEIPT CONTRACT

Schema: pubchem-molecular-weight-source/1.
Fields preserve provider, CID, title, release, endpoint URI, import time, exact raw bytes (Base64),
raw SHA256, importer ID/version, endpoint ID/version, method/version/release, system identity,
original value string/unit, conditions, uncertainty classification/text, source-use metadata,
claim boundary, warnings and errors. The original representation is always distinguishable from
its parsed projection. Import uses CREATE_NEW and FileChannel.force(true); overwrites fail.

The importer selects precisely the computed molecular-weight section and its PubChem-owned reference.
It rejects multiple values, missing/unsupported method or units, additional unknown observation/value
metadata, duplicate JSON keys and trailing JSON. Even malformed input gets a receipt containing its
original bytes and errors. readVerified reconstructs the projection from preserved bytes and import
time, then requires equality; projected values cannot be edited independently of the source unnoticed.
Athena SourceReceipt additionally verifies the raw hash when constructed/deserialized.

REVIEW CONTRACT / CLAIM BOUNDARY

SourceReview explicitly identifies review ID/version, reviewer, review process/version and time,
approval/rejection intent and reason, source subject CID, associated DesignState, endpoint/method/
system/conditions/unit/value-kind Semantics, ScientificStatus, uncertainty category/note, permitted
claim and limitations. Missing mandatory scientific association produces a rejected decision.

Only exact source semantics, matching source subject, POINT_UNKNOWN and SCREENING_ONLY can be
accepted by this one-source adapter. Unsupported source errors cannot be repaired by filling in
convenient review values. A reviewer cannot relabel the endpoint, change units, invent conditions,
upgrade status, invent intervals or strengthen the claim. Explicit rejection remains stored.
The reviewer is responsible for the CID-to-DesignState association: this endpoint does not supply
an atom-correspondence proof, and the adapter does not pretend to infer one from a name or mass.

SourceDecision holds the complete receipt, review, evidence ID/version, resulting Evidence (null
on rejection) and rejection reasons. Its constructor rederives the deterministic decision; altered
serialized evidence/conclusions cannot bypass the recorded review semantics. Successful Evidence
references the provider/CID and raw hash, and retains source release, importer, review process,
warnings and usage limits. Qualification links the exact subject state and review reference.
Exact claim: PubChem-reported COMPUTED molecular weight only. Not experimentally measured mass,
free energy, affinity, potency, functional retention or an ADME claim. Prediction remains separate.

MINIMUM LOCAL GOVERNANCE

registerSourceReview reserves one file per evidence ID/version in an explicitly shared registry
folder. Filename is SHA256 of the encoded [id,version] tuple (no user path interpolation). The file
contains the entire source decision, including rejected reviews, and is forced before return.
CREATE_NEW gives one reservation winner. Reusing exactly the same complete content is idempotent;
different raw data, review or evidence under the same ID/version fails with checked IOException.
Rejected reservations cannot later be silently promoted; use an explicit new evidence version.

Independent codec instances reload the file for comparison. No process-local index can mask a
conflict. Concurrent different reservations have only one winner. A partial/corrupt reservation
fails closed and is never overwritten or deleted automatically; recovery requires manual review.

Governed readKnowledge(path,registry) / writeKnowledge(path,knowledge,registry) require EVERY evidence
item to equal an accepted reservation. Thus an independently authored snapshot cannot silently
rebind an existing evidence ID. A conflicting write is rejected before creating the output file.
Legacy ungoverned codec methods remain for historical compatibility; this new one-source workflow
must use the governed overloads and the same registry directory. This is not a global/distributed
registry, signature system or protection against out-of-band privileged filesystem edits.

UNIT / UNCERTAINTY POLICY

No conversion is needed or performed. Original value text and 'g/mol' survive; every other or missing
unit is preserved in the receipt but rejected as unusable. No unit aliases or normalization library.

Actual records provide point values and no uncertainty. They are POINT_UNKNOWN, with empty reported
uncertainty text. Equal numeric bounds in the reused Phase 2.2 Value merely encode a point and
explicitly do NOT imply zero physical uncertainty. The raw decimal precision is not an error bar.
Malformed/uninterpretable observations are UNAVAILABLE. The review taxonomy distinguishes reported
interval, reported error, qualitative and unavailable states, but this importer does not interpret
those additional formats: unknown annotations fail closed, with raw source intact. No confidence
intervals, confidence scores or experimental conditions are manufactured.

STRICT COMPARABILITY

Phase 2.2 remains unchanged: method/version/parameters, endpoint, system, conditions, units, kind,
status, context and applicable state must satisfy the exact hypothesis requirement. Empty source
conditions mean unreported, not wildcard matching. A requirement for temperature/assay conditions
cannot be satisfied by this receipt. The system may test the narrow computed-property criterion
whose policy requires no unavailable assay context. Parent and product retain their separate CIDs.

LIMITATIONS / PHASE 2.4 RECOMMENDATION

- One computed endpoint and source shape only; no assay ingestion or broad property import.
- Reviewer identity, source origin and molecular association are recorded assertions, not digital
  signatures or automated CID-to-graph certification. The host must use Hermes readVerified before
  review. A hash proves byte integrity, not that a remote provider or reviewer is authentic.
- Registry guarantees apply to cooperating callers using one protected local registry and governed
  codec methods. Independent registries or legacy API bypass are not globally policed.
- CREATE_NEW plus force gives immutable reservations; partial writes fail closed. Automatic crash
  repair, cross-filesystem power-loss guarantees, distributed locking and tamper-resistant audit
  storage are outside scope. Existing partial data is never destroyed automatically.
- Snapshot-local hypothesis versioning and existing source-state applicability remain as Phase 2.2.
- Strict conditions/method/unit equality and unknown uncertainty limit the claim. Support means only
  that the explicitly scoped published-computation predicate is met, not physical certainty.
- Rejection conflicts require a new evidence version; this slice adds no mutable approval workflow.
- The adapter is deliberately source-specific and shared via JSON rather than adding forbidden
  Hermes/Athena production dependencies. No generic ingestion bus or new Maven module was added.

Recommend Phase 2.4 as a separately reviewed host-wiring/attribution checkpoint: select the existing
workflow entry point that will enforce importer verification, the shared registry and durable journal
as one documented protocol, and add reviewed molecular-subject association checks appropriate to the
source's structure data. Do this before broader evidence ingestion or chemistry expansion. Do not
start that work, WELD migration or Hephaestus consolidation automatically. STOP after this commit.
